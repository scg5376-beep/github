# 규칙 · 발전 루프 — 잘되는 플랫폼을 보고 사이트를 스스로 키운다

> 언제: 운영자가 「시작해」라고 하면. 운영자 2026-09-17: "홈페이지 자체는 완성되었으니까 이제 다른 플랫폼이랑 계속 비교해가며 디벨롭 … 중간중간 나한테 보여주기식 완성 및 변경을 주지말고 … 하루에 클로드 max 토큰 25%만 사용해서 … 결국 중요한건 사람들이 유입이 있고 활동성이 있어야한다는거야".

## 목표 하나

**유입(검색·공유로 들어오는 사람)과 활동(머물고 다시 오고 따라 하는 것)이 늘게** 사이트를 바꾼다. 예쁘게가 아니라 들어오고 쓰게.

## 예산 — 토큰 수 (5시간 창의 25% 에 해당하는 양)

- 운영자 2026-09-17: "5시간 한도 기준으로 25%" + "다른 레포들과 사용량을 공유하니 사용 가능한 토큰 수를 정해 놓는 방식". 그래서 **이 프로젝트가 쓴 토큰**(`~/.claude/projects/C--Users-USER-Desktop------/*.jsonl` 의 usage, 캐시 읽기는 1/10)으로 잰다. 다른 레포 사용량은 안 섞인다
- 상한(cap)은 `docs/발전/예산.json`. 앤스로픽이 창의 토큰 수를 공개하지 않아 **첫 실행 때 캘리브레이션**: 이 프로젝트만 돌아가는 동안 Δ토큰/Δ(5시간 %) 를 재서 25%p 에 해당하는 토큰 → cap. 그 전 기본값 500만(잠정). 운영자가 숫자를 주면 `--cap N`
- 「시작해」 → `python site/_build/budget.py --start` · 매 바퀴 끝 → `--check`(종료코드 2 = 멈춤) · 첫날 5시간 %가 3 이상 올랐을 때 → `--calibrate`
- **초과 여유 +10%**(운영자 2026-09-17): `--check` 종료코드 2(상한 도달) = 새 바퀴를 시작하지 않고 하던 바퀴의 검수·배포·기록만 마친다. 종료코드 3(cap×1.1 초과) = 그 자리에서 멈추고 미완성은 일지에 「다음에 이어서」
- 「작업 시작」「시작해」라고 할 때마다 `--start` 로 기준점을 새로 잡고 cap 만큼 진행한다. 한 번에 cap 하나
- 주간 95% 이상이면 무조건 멈춘다. 예산 안에서도 한 바퀴는 **작게**(개선 하나 → 배포 하나)

## 한 바퀴 (반복)

1. **고른다** — `docs/발전/큐.md` 맨 위 항목 하나(참고 플랫폼 + 볼 관점). 큐가 비면 큐 절을 보고 채운다
2. **본다** — 그 플랫폼의 공개 화면을 헤드리스 Edge 로 찍고(`site/_build/shot.mjs`, 로그인 없음) 무엇이 다른지 **측정 가능한 말**로 적는다: 첫 화면에 몇 초 안에 무엇이 보이나 · 한 화면의 글자 수 · 단추 수 · 글 하나의 길이·소제목 수 · 검색 결과에 어떻게 잡히나(제목·설명·구조화 데이터) · 다시 오게 하는 장치(시리즈·목록·업데이트·구독)
3. **가른다** — 우리와 다른 점 가운데 유입·활동에 닿는 것 하나만 고른다. 근거를 한 줄(무엇을 보고 그렇게 판단했나). 디자인 취향 차이는 고르지 않는다
4. **바꾼다** — 해당 규칙 파일(레이아웃·방법글·설명글·글쓰기·근거) 대로. 보안.md 는 언제나. 자바스크립트·폼·외부 자원·돈은 여전히 금지 — 활동성 장치가 그것을 요구하면 「운영자 결정 필요」로 큐에 남기고 다음 항목으로
5. **검수·배포** — 공통_마무리.md 그대로(검사 0·전수 검사 0·두 폭 캡처·cleanup)
6. **적는다** — `docs/발전/일지.md` 에 한 줄: 날짜 · 참고 플랫폼 · 본 것 · 바꾼 것 · 커밋 · 예산 사용률. 운영자에게 **중간 보고를 보내지 않는다**. 하루 끝에 한 번, 표 하나로

## 실험의 목표 (운영자 2026-09-18)

> "나는 AI자가발전 자가피드백으로 어디까지 홈페이지가 운영될 수 있나 이게 궁금해 유입이 정말 생기고 대형포털이 실제로 생겨날 수 있나? 이 목표를 향해 갔으면 좋겠어 지금 나는 솔직히 디자인이나 문단나눔 가독성 보기편한그런느낌 AI티 벗어던지고 사람들이 실제로 여기서 자료를 인용하고 찾아보고 활용하게 끔 AI가 자가로 만들 수 있을지 이게 너무 궁금해서 실험하는거야"

바퀴의 판단 기준은 「원문 하나 더」가 아니라 **「사람이 실제로 찾고, 읽고, 인용할 것인가」**다. 그래서:

1. **신호를 직접 잰다** — 매 회차 시작에 `docs/발전/신호.md` 를 갱신한다.
   - 네이버 웹검색 목표 검색어 30개(`docs/발전/검색어.md`)에 우리 URL이 있나, 몇 번째인가 (NaverSearch MCP `search_webkr`)
   - `site:` 조회로 네이버 색인 쪽수, 구글은 서치 콘솔 캡처(운영자)
   - GA4 방문·페이지(운영자가 읽기 권한을 주면 직접, 아니면 캡처)
   - 다른 사이트가 우리를 링크·인용한 수 (`search_webkr "sajangmarketing.com" -site:`)
2. **가독성 회차를 콘텐츠 회차 사이에 끼운다** — 3바퀴에 1바퀴는 글 하나를 400폭으로 캡처해 눈으로 읽고(ko-tone 순서), 문단·제목·표·강조를 사람이 쓴 안내문처럼 고친다.
3. **검색어 → 글** 순서로 만든다. 사람이 치는 말(지식iN·자동완성)에서 출발해 그 말이 제목·설명에 있는지 본다.
4. 신호가 움직이지 않는 갈래는 접고, 움직이는 갈래에 바퀴를 몰아 준다.
- 수집요청 대기 목록(2026-09-20): 새 글을 만들면 `docs/발전/수집요청.md` 1순위에 주소를 넣는다. 마지막 보고에서 운영자에게 「붙여넣기」로 한 번에 넘긴다. 제출된 5쪽이 몇 시간 만에 색인된 것이 근거.

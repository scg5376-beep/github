# 4단계 · 품목 레포 만들기 (실험은 여기서 합니다)

> **지식은 한 곳에, 실험은 품목마다.** 이렇게 나누는 이유가 있습니다.
> 품목이 늘어도 **판단 기준은 한 곳**이어야 하기 때문입니다.

## 레포가 둘로 나뉩니다

```
marketing-doctor        컨트롤 타워
                        · 지식을 모으고 갱신합니다
                        · 이 스킬을 만들어 내보냅니다
                        · 실전 기록을 받아 쌓습니다 (실전/품목/)

품목-○○                 실행·실험
                        · 이 스킬을 복사해 갑니다
                        · 실제로 글 쓰고 팔고 광고합니다
                        · 주간 기록을 채워 컨트롤 타워로 되돌려 보냅니다
```

**규칙이 품목 레포에서 갈라지면 안 됩니다.** 품목 A 에서 고친 판단을
품목 B 가 모르면, 같은 실수를 두 번 하게 됩니다.

## 새 품목을 시작할 때

```
1  품목 레포를 만듭니다 (이름에 상호·지역을 넣지 않습니다)
2  이 스킬 폴더를 통째로 복사해 넣습니다
      품목 레포/.claude/skills/product-launch/
   블로그를 같이 하실 거면 naver-blog 스킬도 함께 복사합니다
3  references/0-팔-수-있는-상태인가.md 를 끝까지 닫습니다
4  레포 안에 보고/ 폴더를 만들고 컨트롤 타워의 실전/양식/ 세 파일을 복사해 넣습니다
      보고/품목.yaml  ·  보고/주간.csv  ·  보고/기록.md
5  품목.yaml 을 채웁니다 (시작할 때 한 번)
6  주 1회 주간.csv 에 한 줄, 기록.md 에 한 덩어리를 이어 붙입니다
7  월 1회 보고/ 를 컨트롤 타워에 보냅니다
```

## 스킬을 고쳐야 할 일이 생기면

**품목 레포에서 고치지 않습니다.** 컨트롤 타워에서 고치고, 다시 복사해 갑니다.

```
품목 레포에서 발견   →  컨트롤 타워에 알린다  →  거기서 고친다  →  전 품목이 다시 받는다
품목 레포에서 고침   →  그 품목만 달라진다   →  나중에 어느 게 맞는지 모른다  ← 이걸 막습니다
```

## 되돌려 보낼 때 빼는 것

```
❌ 손님 이름·전화번호·주소     집계된 수만 보냅니다
❌ 상호·지역                  컨트롤 타워의 검사기가 잡습니다
❌ 계정 아이디·비밀번호·토큰
```

## 품목 레포에 두는 것 / 컨트롤 타워에 두는 것

| | 품목 레포 | 컨트롤 타워 |
|---|---|---|
| 스킬 | 복사본 (읽기만) | **원본** |
| 실제 글·상세페이지 | ○ | × |
| 광고 소재 | ○ | × |
| 주간 기록 | 원본을 쓴다 | **모아서 쌓는다** |
| 판단 기준·근거 | × | **○** |

**의심스러우면 컨트롤 타워를 봅니다.** 거기가 맞습니다.

## 컨트롤 타워는 여기에 쓰지 않습니다

받아서 **읽고 분석만** 합니다. 분석 결과도 이 레포에 밀어 넣지 않고
컨트롤 타워의 `실전/분석/` 에 씁니다. 그걸 보고 **할지 말지는 이 레포가 정합니다.**

양쪽에서 고치면 어느 쪽이 맞는지 알 수 없게 되기 때문입니다.

## 보낸 게 반려되면

컨트롤 타워의 `엔진/report_check.py` 가 이런 걸 잡습니다.

```
· 헤더가 계약과 다름 · 주차가 빠지거나 겹침
· 한 주에 둘 이상 바꿈           → 그 주는 분석에서 뺍니다
· 주문은 있는데 정산액이 빔
· 손님 정보·상호·전화번호가 섞임   → 받지 않습니다
```

**컨트롤 타워가 대신 고치지 않습니다.** 여기서 고쳐 다시 보냅니다.

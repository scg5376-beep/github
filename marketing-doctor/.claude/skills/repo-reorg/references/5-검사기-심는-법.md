# 5단계 · 검사기를 심는다

> **구조는 사람이 지키지 않는다.** 바쁘면 규칙을 잊는다. 그게 정상이다.
> 그래서 마지막에 **검사기를 레포 안에 심고, 커밋 전에 돌리는 습관**을 만든다.

## 진단 도구를 레포로 옮긴다

```
1  도구/구조진단.py 를 레포 안에 복사한다  (예: 도구/ 또는 scripts/)
2  파일 맨 위 상수를 그 레포에 맞게 고친다
       상한 · 폴더상한 · 깊이상한 · 항상로드 · 보관성폴더
3  README 나 CLAUDE.md 의 "커밋 전에" 자리에 한 줄 넣는다
```

**상한을 그 레포에 맞게 고치는 게 핵심이다.** 남의 숫자를 그대로 쓰면
매번 걸리고, 매번 걸리면 사람이 검사기를 무시하게 된다.

## 검사기가 잡아야 할 것을 그 레포 말로 적는다

일반 도구가 못 잡는 건 **그 레포만의 규칙**이다. 작은 검사기를 따로 만든다.

```
· 앞머리(frontmatter)의 필수 칸이 비었나
· 목차에 없는 폴더가 생겼나            ← 이게 특히 값어치 있다
· 이 레포에 들어오면 안 되는 말이 섞였나 (다른 사업체 이름 · 개인정보 · 열쇠값)
· 서로 가리키는 두 값이 어긋났나        (등급 · 상태 · 경로)
```

★ **"목차에 없는 폴더가 생겼나" 를 꼭 넣는다.** 폴더가 조용히 늘어나는 게
구조가 무너지는 첫 신호다.

## 규칙을 두 곳에 쓰지 않는다 — 검사기끼리도

검사기가 둘 이상이면 **같은 판정 규칙을 복사하지 않는다.** 하나에서 불러 쓴다.

```python
import brand_check as BC        # 판정 규칙은 저기 한 곳에만 있다
... BC.전화.findall(줄) ...
```

복사해 두면 한쪽만 고치게 되고, 그때부터 두 검사기가 다른 말을 한다.

## 내려보낼 때 — 지시가 서로 반대면 안 된다

컨트롤 타워가 개선을 내려보낼 때 **한 지시문 안에서 말이 어긋나면 받는 쪽이 멈춘다.**
실제로 이런 일이 있었다.

```
"도구를 여기서 고치지 말고 무엇이 문제인지 알려라"     ← 앞
"'대장' 성격을 만들어라"                              ← 뒤. 도구를 고치라는 말이다
```

받은 쪽이 **도구를 고치지 않고 명세만 남긴 게 맞다.**
보내기 전에 지시문 안에서 서로 부딪히는 줄이 없는지 한 번 읽는다.

## 검사기를 넓힐 때는 반드시 되짚어 본다

오탐이 나와서 규칙을 느슨하게 만들었으면, **진짜를 여전히 잡는지 확인한다.**

```
1  오탐이 나는 문장을 예외로 넣는다
2  진짜 걸려야 하는 값을 일부러 넣어 본다
3  여전히 잡히는지 확인하고 지운다
4  넓힌 이유를 코드 주석에 날짜와 함께 적는다
```

**실제로 겪은 것** — 검사기가 인용문 속 "간략한 설명으로 1-2개의" 를 주소로 잡았다.
인용문은 고칠 수 없으니 검사기를 넓혔고, 넓힌 뒤 진짜 주소를 넣어 여전히 잡히는 걸
확인하고 지웠다. **확인 기록에 그 예시 주소를 그대로 적었더니 검사기가 또 잡았다 —
옳게 동작한 것이다.** 기록에도 진짜 형태의 값을 적지 않는다.

## 커밋 전 한 줄로 만든다

```bash
python3 도구/구조진단.py .        # 구조
python3 도구/○○_check.py         # 이 레포만의 규칙
```

**이 두 줄을 README 와 CLAUDE.md 의 같은 자리에 적는다.**
사람이 잊어도 다음 사람이 본다.

## 경로를 검사하는 검사기 — 반드시 뺄 것 넷

"문서가 가리키는 경로가 실제로 있나" 는 값어치가 크다.
실제로 만들자마자 **아무도 못 보던 어긋남 여덟을 잡았다** — 대기열이 가리키는 글 넷이
다른 폴더에 있었던 것 같은, **사람 눈으로는 안 보이는 자리**다.

그런데 그냥 만들면 오탐이 수백 건 나온다. 실제로 **949건에서 시작해 8건까지 좁혔고,
좁힌 과정이 그대로 예외 규칙이 됐다.**

```
□ 이력 문서        작업로그 · 결과보고 · 실측 · 인수인계
                   "그때는 이 경로였다" 를 적어 두는 게 목적이다
□ ⛔ 폐기 구간     원문을 남기려고 표시만 얹은 절. 그 안의 경로는 없는 게 정상이다
□ 설계상 지워지는 자산   임시 산출물처럼 며칠 뒤 정리되는 것
□ 자리표시·줄임표   `posts/날짜-브랜드.md` · `insta/메타/...` · gitignore 패턴 · 도메인
```

**슬래시가 있는 것만 경로로 본다.** 맨 파일명은 대개 이름을 부른 것이지 링크가 아니다.
**문서 제 폴더 기준도 같이 본다** — 같은 폴더의 파일을 가리킬 때가 많다.

★ 오탐을 줄일 때는 **한 번에 한 규칙씩 빼고 건수를 적어라.** 그 표가 곧 문서다.

## ★ 검사기가 좋은 행동을 벌하고 있지 않은지 본다

정리 기록을 남겼더니 **'고칠 것' 이 55 에서 57 로 늘었다** (2026-09-02).
보고서가 일반 글 상한(6,000자)에 걸린 것이다.

**기록을 남기는 행위가 점수를 나쁘게 만드는 구조였다.**
그러면 사람은 기록을 안 남기게 된다. 검사기가 정확히 반대로 작동한 것이다.

```
검사기를 심고 나서 한 번 물어본다
  □ 지금 이 검사기가, 우리가 바라는 행동을 벌하고 있지 않나
     기록 남기기 · 근거 붙이기 · 원문 보관 · 반증 적기
  □ 벌하고 있으면 성격을 하나 만든다. 그 행동을 줄이지 않는다
```

이 도구는 `정리기록/` `기록/` `history/` 같은 폴더를 **'기록' 성격**으로 따로 잡고,
**깨진 링크 검사에서도 이력 문서와 ⛔ 폐기 구간을 뺀다.**
다른 이름을 쓰면 설정의 `성격패턴` 에 넣는다.

⚠️ **같은 함정을 두 단계 연속으로 밟은 적이 있다.** 기록 폴더에서 한 번,
경로 검사기에서 또 한 번. **검사기를 하나 만들 때마다 물어라.**

## 검사기가 통과한다고 내용이 맞는 건 아니다

```
검사기가 보는 것    구조 · 형식 · 중복 · 경로
검사기가 못 보는 것  사실이 맞나 · 최신인가 · 서로 말이 되나
```

**형식 검사를 통과했다고 정리가 끝난 게 아니다.** 마지막에 사람이 읽는다.
